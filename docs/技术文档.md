- Android Studio 原生应用，离线单机、手机竖屏；API24 是最低兼容版本，不等于 compileSdk/targetSdk 必须为24。

- core 不依赖 Android、Context、Compose 或 DataStore。规则引擎为可测试的状态转移；内容与随机源以接口注入。
- 数据存储使用 typed DataStore + kotlinx.serialization 保存完整单槽快照。此体量不引入 Room、服务器、账户、网络 API、Unity 或 WebView。
- 日期使用 java.time 并配置 API24 所需 coreLibraryDesugaring。日期来自252工作日表，不使用系统时间推进。
- 金额使用 Long 分，输入通过十进制解析；BigDecimal 执行利息/返还并 HALF_UP 到分，拒绝溢出与非法格式。不得使用 Double 存钱。赔率保存十进制定点值，例如1.9存为19个十分位。
- 初期手动依赖注入即可。UI 导航和业务阶段分离，不以导航栈表示待发工资/奖励。

建议目录：core/model、core/rules、core/content、core/validation；app/ui、app/presentation、app/data/content、app/data/save、app/di。导出工具放 tools，创作源留 assets，不在 APK 内解析 XLSX。

## 3. 状态模型与命令

GameState 持久化：saveSchemaVersion、rulesVersion、contentVersion/hash、saveId、revision；当前工作日索引、业务阶段、待处理事件/弹窗步骤；现金债务、六属性、运气峰值；全局成功/失败数、连续失败数、审阅次数与正确次数、待发三成功奖励；保底档位及周期计数；本月有效工资、待生效涨薪、已触发晋升档；已发薪月份/奖金年份/利息年份；未选健康月份数、低多巴胺月份数、本章健康/英语选择标记；竞猜递增上限、投注快照、已结算市场ID、已兑现次数、选项排列映射；随机种子/算法版本/状态；当前分页、各候选人标记、是否使用运气、上一审阅/录用双结果、结局及原因码。

Candidate、Answer、ReviewStatement、ReviewEvidence、JobDemand、News、Workday、Market、MarketOption 使用稳定 ID 和显式外键。浏览中的卡片索引决定当前提交对象；每份候选人标记单独持久化，分页切换不串用标记，滑动中不得提交。审阅答案属于内容模型，仅通过 UI 能力阈值控制自动提示；不声称客户端数据具备防逆向保密能力。

命令包括 BrowseCandidate、MarkStatement、SetLuckUsage、SubmitCandidate、ChooseSuccessReward、PlaceBet、AcknowledgeEvent、RepayDebt、FinishEconomy、ChooseMonthlySkill、AcknowledgeEnding、StartNewGame。提交必须匹配当前完整显示的候选人与该人的已保存标记；有效但未标记的 statementId 也拒绝。每条命令验证阶段、saveId/revision 与幂等键。危险支出二次确认绑定当前余额、金额与 revision，状态改变后重新预览。

阶段示例：Opening → DayEntry → EventNotice → Recruiting → SuccessReward（如需）→ MonthIncome → Repayment → InterestCheck → MonthlySkill → GrowthCheck → FinalCheck/DayEntry。进入任何 Ended 后冻结；期间新闻页只是阅读视图。DayEntry 先结旧竞猜、检查即时结局，再处理当天固定事件，再允许新竞猜/招聘；不得把下一日的事件提前执行到本月面板之前。

一次命令在单一串行处理器内完成：验证 → 计算新状态（含抽样、结果、财务、下一待处理步骤）→ 原子保存 → 发布成功 UI。保存失败保留旧状态、显示可重试错误，禁止先显示结果再异步保存。随机源可注入、可复现；提交重试、进程死亡不得重抽，重复结算不得重复加钱。DataStore updateData 的变换应保持纯净，不在可重试回调内推进外部随机源。

存档错误不能静默重置。未知 schema、规则或内容版本要求明确提示重开，用户确认前保留旧文件。新建游戏覆盖旧单槽前确认。结束页必须完成一次独立点击才能回主页，避免触发结束的手势穿透。
